The obvious answer, and why it fails

Point a computer-use model at the screen every time?

NOT REPRODUCIBLE

~1 in 6

Frontier models now beat the human baseline on OSWorld (72.36%) and still fail roughly one task in six. That is a fine assistant and an unacceptable unattended teller.

NOT AFFORDABLE

per click

A model round-trip for every step, times thousands of exception items a day.

NOT AUDITABLE

SR 11-7

The institution must perform its own outcomes testing on a vendor's model.

It has been tried at scale and withdrawn. OpenAI's Operator launched Feb 2025 and shut down Aug 2025. Adept raised $415M+ and was absorbed into Amazon. General-purpose agentic browsing has not found a durable enterprise buyer.

The thesis
You cannot outcomes-test a system that does not produce the same output twice.

In this market determinism is not a nice-to-have. It is the precondition for the examiner signing off at all.

So put the model where it is genuinely good — reading an unfamiliar screen once and working out what a trained operator would do — and take it out of the path where determinism is the requirement.

the model discovers→ the artifact is the capability→ deterministic replay is how it runs in production
How it works

The model chooses which control.
Swivel decides how it is described.

WHY NOT ASK THE MODEL FOR A SELECTOR

  • Quality varies run to run — artifact durability becomes non-deterministic.
  • It cannot see geometry, so it reaches for the DOM id: the weakest evidence available.
  • It does not know which on-screen value came from a parameter, so it hardcodes one member's number into a capability meant to serve all of them.

WHAT IS ACTUALLY STABLE

What a human operator uses: what the control is, what it is called, what it is near.

Scored at replay time. Below threshold, or too close to call, the engine refuses rather than guessing — and reports which evidence went missing. That report is also the earliest available drift signal.

Errors are the product

“No such member” is an answer, not a crash.

Conflating the two is the most common way this kind of system goes wrong. The result type makes it impossible.

Signals are authored once per vendor product, not per capability. Symitar times out the same way for every credit union running it. Ten capabilities share one definition of “your session expired”; when the vendor changes that screen, one profile changes and every capability inherits the fix.

Human in the loop

The session stays alive. Control moves.

NOT A TICKET QUEUE

When the engine refuses to guess, it pauses — and the browser session is still there, mid-flow, with whatever the application has built up server-side. The operator gets a live screencast of that session and drives it. A handoff that starts fresh hands the operator the problem of getting back to where the automation was.

WHO IS IN CONTROL IS ENFORCED

A single-writer lease, wrapped around the surface, so acting without the token is impossible — not merely discouraged. Observation stays open to everyone; only mutation is gated. A stale tab or a second operator cannot interleave keystrokes into a funds-transfer form.

Measured, not described: the same artifact replayed at a second institution refused one control it could not identify, escalated, a human did that step by hand in the live session, handed control back — and the automation finished the remaining steps itself. Every forwarded click is on the run's evidence chain.

Next: promote those recorded rescues into reviewed step patches, so each escalation is the last of its kind across every tenant.

The compounding advantage

One artifact. Hundreds of institutions.

Many tenants run the same vendor product, branded and versioned differently. Rebuilding per tenant is 100 × 20 × 10 = 20,000 recordings. As base capabilities plus overlays it is ~200 recordings and 20,000 small, reviewable patches.
